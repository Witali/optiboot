# Optiboot Mini: протокольные расширения для ATmega328P (эксперимент)

Дата: 28 октября 2026. База: собственный ассемблерный Optiboot Mini на **358 байт** (`optiboot_mini328_358.S`). Полный образ всегда занимает 512-байтную загрузочную область `0x7E00..0x7FFF`, с двухбайтной версией `03 08` по адресу `0x7FFE`. Лицензия производного кода GPL-2.0-or-later; см. COPYING.

**Экспериментальные сборки не проверены на настоящем ATmega328P, ни штатным avrdude на физическом UART.** Проверены машинные инструкции в ограниченном программном интерпретаторе AVR, который моделирует EEPROM, специальные чтения LPM и Flash.

## Образы

| Образ | Код | Версия | Занято | Свободно из 512 | Особенности |
|---|---:|---:|---:|---:|---|
| исходный Mini | 356 | 2 | 358 | 154 | Базовые загрузка/чтение Flash |
| `optiboot_328_diag` | 478 | 2 | **480** | **32** | + EEPROM READ, + read-only UNIVERSAL, + SET_PARAMETER framing |
| `optiboot_328_diag_signon` | 509 | 2 | **511** | **1** | То же + GET_SIGN_ON (строка `AVR STK`) |

Основной экспериментальный вариант для развития — **480-байтный**: вариант на 511 байт почти не оставляет резервов, а GET_SIGN_ON обычному avrdude не нужен.

## Реализовано в новых диагностических сборках

* `STK_READ_PAGE` (`0x74`) с `memtype='E' (0x45)`: читает *настоящую* EEPROM через EEAR/EEDR/EECR, без 128-байтного буфера SRAM. Для ATmega328P используется уже пересчитанный в байты адрес после `STK_LOAD_ADDRESS`; в avrdude он для ATmega328P передаётся как слово (см. https://github.com/Optiboot/optiboot/issues/235 ). Поддержан размер 1..256 байт, 0 (младший байт длины) по старой семантике даст 256.
* `STK_UNIVERSAL` (`0x56`): ровно четыре входных байта и один выходной байт. Специальная поддержка **только безопасных запросов чтения**:
  * `50 00 00 00` -> low fuse (SPMCSR.BLBSET=1, Z=0);
  * `50 08 00 00` -> extended fuse (Z=2);
  * `58 00 00 00` -> lock byte (Z=1);
  * `58 08 00 00` -> high fuse (Z=3);
  * `30 00 n 00` (n = 0,1,2) -> реальный байт сигнатуры через SPMCSR.SIGRD (Z=0,2,4).
  * Все прочие комбинации возвращают нулевой байт как исходный Optiboot, без ложных реальных записей fuse/lock.
* `STK_SET_PARAMETER` (`0x40`): **принимает два параметра и отсылает INSYNC/OK, но фактически не сохраняет параметр**. Это совместимый no-op, а не полноценное изменение настроек STK500.
* В сборке `*_signon` дополнительно `STK_GET_SIGN_ON` (`0x31`) возвращает `0x14 + 'AVR STK' + 0x10` согласно AVR061. Семибайтная строка размещена по абсолютному Flash-адресу `0x7FF6`; сборочный скрипт автоматически проверяет его неизменность, чтобы не допустить тихого повреждения ответа при изменении исходника.

Не менялось: FLASH PROG_PAGE/READ_PAGE, STK_GET_SYNC, GET_PARAMETER, SET_DEVICE/EXT, LOAD_ADDRESS, READ_SIGN, LEAVE_PROGMODE, контроль `CRC_EOP`, WDT, UART FE0, аппаратный временный буфер SPM без дополнительного SRAM.

## Чего пока нет и почему

* **EEPROM PROG_PAGE** не реализована. В отличие от 128-байтного временного аппаратного буфера Flash, EEPROM на ATmega328P не имеет аналогичного буфера для предварительной проверки `CRC_EOP`. Чтобы сначала проверить пакет, а затем начать запись EEPROM, нужен приёмный буфер в SRAM или дополнительная протокольная схема/ограничение длины блока. Потоковая запись без SRAM возможна, но при обрыве пакета часть EEPROM уже будет перезаписана; для загрузчика с приоритетом надёжности это неприемлемо как вариант по умолчанию.
* Альтернатива без блока SRAM: поддержать однобайтовую стандартную команду `STK_PROG_DATA (0x61)` (один байт данных + EOP). Это потребует реализации программирования EEPROM и инкремента адреса, плюс программного клиента, который использует именно однобайтовые операции. Обычный avrdude для ATmega328P, как правило, использует `PROG_PAGE`.
* `READ_FUSE (0x72)`, `READ_FUSE_EXT (0x77)`, `READ_LOCK (0x73)` как самостоятельные команды не реализованы; требуемые данные доступны через `STK_UNIVERSAL`.
* `READ_OSCCAL (0x76)` можно добавить посредством SIGRD/Z=1, но не вместилось вместе со всем остальным в 511-байтный образ.
* `STK_CHIP_ERASE (0x52)` оставлен без реального действия, как и в базовом Optiboot. Программное стирание всех страниц приложения через SPM не эквивалентно ISP Chip Erase и опасно для функции самовосстановления. Программировать fuse-биты из загрузчика через SPM нельзя.
* `STK500v2` — **другой протокол**, а не ещё одна команда, он требует отдельного загрузчика/переписывания ПК-инструмента.

## Воспроизводимые программные проверки

```bash
python3 build.py optiboot_328_diag optiboot_328_diag_signon
python3 differential_diag.py
python3 test_diag.py
```

* Сборка 480 байт, код 478; сборка 511 байт, код 509. Для обеих проверен неизменный адрес двух байтов версии.
* На каждой версии **549** сравнений с исполняемым оригинальным Optiboot HEX на неизменённых командах: ответы байт-в-байт и Flash в модели совпадают. Новые команды с намеренно изменённой семантикой в это сравнение не включаются.
* **26/27** функциональных обменов на каждой версии для нового кода (EEPROM READ, UNIVERSAL fuse/lock/signature, SET_PARAMETER, дополнительно GET_SIGN_ON), плюс базовые FLASH PROG/READ и WDT.

Эмулятор ограничен: нет физического UART, нет электрических задержек EEPROM/SPM, нет полной проверки таймингов AVRs и всех вариантов ошибок. По этой причине не рекомендуется прошивать новые версии без доступного ISP-программатора и возможности восстановить исходную прошивку.

## Следующий этап

1. Испытать EEPROM READ и `UNIVERSAL` на физической ATmega328P с программатором ISP для восстановления.
2. Если нужна запись EEPROM в обычном avrdude, сделать отдельную сборку с 128-байтным **SRAM-буфером только для EEPROM** (Flash по-прежнему без RAM), с проверкой EOP до первого байта записи. Затем проверить реальный размер, который может не поместиться в 512 байт без отказа от некоторых диагностических команд.
3. Если нужен нулевой дополнительный SRAM даже при записи EEPROM — рассмотреть `STK_PROG_DATA` по одному байту с проверкой EOP перед записью и хостовым приложением, которое использует этот режим.
